MLX Speculative Decoding Tests Whether Apple Silicon Can Close the Local LLM Speed Gap

MLX's new speculative decoding may finally close Apple Silicon's local LLM speed gap—if draft-model acceptance beats Metal's verification overhead.

August 14, 2026 · 10:05 PM PDT · 6 min read · 12 sources · Original family: M Series Apple Silicon LLM Inference
MLXspeculative decodingtoken latencyApple Silicon
Editor’s brief

Why this matters now

Speculative decoding has been a cloud-serving staple for two years, but Apple Silicon only got a production-grade implementation in mlx-lm 0.21. This article examines whether that release, plus newer drafters like DFlash and Apple's ReDrafter, materially improves token latency on Macs. Evidence comes from community benchmarks, GitHub repositories, Apple's research blog, arXiv preprints, and a documented llama.cpp regression test. The picture is mixed: MLX-based setups show real gains, but Metal's parallel verification overhead can erase them when acceptance rates are low.

Assignment angle: This shifts the story from M5 memory-bandwidth scores to whether draft-model verification in MLX materially improves token latency on Apple Silicon.

FIELD NOTE

The MLX 0.21 Breakthrough and Its Limits

mlx-lm 0.21 shipped a production-grade speculative decoding implementation, ending the era when Apple Silicon users had to rely on llama.cpp's experimental draft support or skip the technique entirely. The core mechanism is unchanged from CUDA: a small draft model proposes multiple tokens, and a larger target model verifies them in parallel. Sources claim 2-3x speedups with exact output distribution equivalence. But the first community reports caution that the gain is not automatic. A DFlash-based experiment on MLX found that when acceptance is low, the overhead of the draft model and verification is wasted, and throughput can fall below baseline.

  • mlx-lm 0.21 introduced production-grade speculative decoding for Apple Silicon.
  • Speculative decoding uses a draft model to propose tokens and a target model to verify them in parallel.
  • Claimed speedups are 2-3x with mathematically exact output, but low acceptance rates can make throughput fall below baseline.
  • DFlash, a block-diffusion drafter, generates 16 tokens in one pass and verifies them in one pass, with lossless output.

FIELD NOTE

MLX vs. llama.cpp Metal: Verification Overhead Decides

The most striking conflict in the evidence is between llama.cpp and MLX on Apple Silicon. A documented test on an M1 Max running Qwen3.5-9B measured a ~25.3 tok/s baseline, and every speculative configuration in llama.cpp came in below it, from -11% to -24%. That test, filed as llama.cpp issue #23752, suggests Metal's parallel verification path can be a net loss. In contrast, an MLX-based setup with Qwen 3.6 27B and native multi-token prediction went from 10.5 tok/s on llama.cpp to 18.3 tok/s with MTPLX. The difference is not just the framework—it is whether the draft model's acceptance rate is high enough to amortize the verification cost.

  • llama.cpp's MTP speculative decoding on Metal was a net loss at every setting in a documented M1 Max test.
  • The same baseline model showed -11% to -24% throughput with speculative decoding enabled.
  • An MLX setup with Qwen 3.6 27B and native MTP reached 18.3 tok/s, up from 10.5 tok/s on llama.cpp.
  • Acceptance rate is the key variable: low acceptance makes verification overhead dominate.

FIELD NOTE

Draft-Model Fit and the New Speculation Engines

Apple Silicon's unified memory changes how draft models must be chosen. Cross-family pairs with mismatched tokenizers are still underexplored, and an arXiv preprint extends MLX-LM with Universal Assisted Generation to handle them. Meanwhile, three speculation engines are emerging: Prompt Lookup Decoding (on by default for any model), the Gemma 4 cross-attention drafter, and Qwen 3.6's native multi-token-prediction head. Apple's own ReDrafter uses an RNN draft model conditioned on the LLM's hidden states, with dynamic tree attention over beam search. These engines differ in acceptance rate and memory footprint, and none is a universal win.

  • Prompt Lookup Decoding is on by default and works with any model.
  • Gemma 4 cross-attention drafter and Qwen 3.6 native MTP head are two other speculation engines.
  • Apple's ReDrafter uses an RNN draft model and dynamic tree attention over beam search.
  • Cross-family tokenizer mismatches remain underexplored; Universal Assisted Generation extends MLX-LM for them.

What the Benchmarks Actually Measure

The available benchmarks are mostly community-driven and not yet standardized. One production-style acceptance kit tracks acceptance rate, decode P95, unified memory swap ceilings, llama.cpp Metal parity, and a remote Mac offload matrix. Another systematic study across three Apple Silicon machines covers quantization ladders and speculative decoding. The numbers vary by model, draft model, and memory pressure. The 18.3 tok/s result for a 27B model is a single blog report, not a controlled benchmark. The DFlash experiments show that throughput can fall below baseline when acceptance is low, so headline speedups are conditional.

↗ Where it could go

  • mlx-lm 0.21's production-grade implementation could make speculative decoding a standard local inference feature.
  • Apple's ReDrafter and block-diffusion drafters like DFlash may push acceptance rates high enough to overcome Metal overhead.
  • Native multi-token-prediction heads in models like Qwen 3.6 can deliver 18+ tok/s on 27B models without cloud GPUs.
  • Cross-family drafters like Universal Assisted Generation could make any small model usable as a drafter on unified memory.

△ What could go wrong

  • Low acceptance rates can make throughput fall below baseline, as shown in DFlash experiments.
  • llama.cpp's Metal backend already shows speculative decoding as a net loss, signaling framework-specific pitfalls.
  • Unified memory swap ceilings may cap gains when draft and target models compete for bandwidth.
  • Community benchmarks are not standardized, so headline speedups may not generalize across Macs and models.

Closing read

Conclusion

The evidence shows that MLX's speculative decoding is real and can improve token latency on Apple Silicon, but it is not a guaranteed speedup. The documented llama.cpp regression on Metal proves that verification overhead can erase gains, and the DFlash experiments confirm the same risk in MLX. The most reliable wins come from high-acceptance drafters like Qwen's native MTP head or Apple's ReDrafter, which are designed to fit the target model's distribution. Whether Apple Silicon can close the local LLM speed gap depends on draft-model fit and memory bandwidth, not just on the existence of speculative decoding.

Five takeaways

  • mlx-lm 0.21 is the first production-grade speculative decoding implementation for Apple Silicon.
  • Speculative decoding can deliver 2-3x speedups, but only when acceptance rates are high enough to amortize verification.
  • llama.cpp's Metal backend showed a net throughput loss with speculative decoding in a documented M1 Max test.
  • MLX setups with native MTP heads have reported 18.3 tok/s on a 27B model, up from 10.5 tok/s on llama.cpp.
  • Acceptance rate, draft-model fit, and memory bandwidth—not just the technique itself—determine whether Apple Silicon closes the speed gap.
