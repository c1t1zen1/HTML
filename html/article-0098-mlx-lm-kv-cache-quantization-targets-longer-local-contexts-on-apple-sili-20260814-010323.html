MLX-LM KV-Cache Quantization Targets Longer Local Contexts on Apple Silicon Macs

Quantizing KV caches—not weights—lets MLX-LM stretch context windows on Apple Silicon, with TurboQuant ports promising 5x compression and faster long-context inference.

August 14, 2026 · 1:03 AM PDT · 7 min read · 12 sources · Original family: Quantized LLMs Running on Mac Hardware

Editor’s brief

Why this matters now

This article examines a distinct angle in local LLM optimization on Apple Silicon: quantizing the inference-time KV cache rather than model weights. While weight quantization is widely discussed, the KV cache—which grows with every generated token—often becomes the real memory bottleneck at long contexts. Evidence gathered from GitHub ports, blog tutorials, and benchmark reports shows that MLX-LM and related runtimes now expose KV-cache quantization flags, and TurboQuant implementations claim up to 5.5x compression with quality preservation. The unifying theme is Apple's unified memory architecture, where weights, activations, and the KV cache share one physical pool, making cache compression a direct lever for extending context windows.

FIELD NOTE

The Unified-Memory Bottleneck and Why KV Caches Matter

Apple's MLX framework is built around unified memory: model weights, the KV cache, and activations all live in one physical pool shared by the CPU and GPU (source 7). This design enables fast dispatch but imposes a hard limit on total working set. A 26B parameter model consumes roughly 27 GB for weights alone, and every token generated appends to the KV cache—at context lengths above 16K, that cache can rival the model size itself (source 9). Traditional weight quantization reduces the static footprint, but the KV cache grows dynamically, so capping or compressing it becomes essential for long local contexts (source 1).

  • Unified memory means KV cache competes directly with weights for the same finite pool.
  • At context lengths above 16K, the KV cache can rival model size (source 9).
  • Weight-only quantization does not address the dynamic growth of the cache.
  • MLX-LM optimization guides recommend capping KV-cache size as a practical lever (source 1).

KV-Cache Quantization Mechanics: Precision, Group Size, and Codebooks

MLX-LM's server exposes explicit KV-cache quantization flags: --kv-cache-quant q8, --kv-cache-group-size 64, and --paged-kv-cache true (source 5). The group size parameter controls how many KV cache elements share a quantization scale and zero point—a detail that matters more than documentation suggests (source 5). TurboQuant, originally from Google Research, compresses KV cache entries from 16-bit floats down to 3-bit using a Lloyd-Max codebook, and an MLX port achieves up to 5.5x compression (source 2, 9). The MLX implementation offers two paths: V2 uses hardware-accelerated mx.quantized_matmul for speed, while V3 uses the paper-correct Lloyd-Max codebook for maximum quality (source 2).

  • MLX-LM server flags include --kv-cache-quant q8 and --kv-cache-group-size 64 (source 5).
  • Group size controls how many cache elements share scale/zero-point parameters (source 5).

TurboQuant on MLX: Ports, Performance, and Integration Paths

Multiple independent ports bring TurboQuant to Apple Silicon. One port, mlx-turboquant, claims 5x KV-cache compression and up to 3.7x faster inference at long contexts, with 100% identical output quality (source 8). It includes a native C++/Metal GPU kernel that computes attention directly from compressed data without ever decompressing it (source 8). Another reproduction, turboquant-mlx, focuses on MLX-native ops with a custom Metal kernel for fused QJL sign-bit scoring (source 2). As of late March 2026, five integration paths exist for running TurboQuant on macOS, with maturity varying widely; the most accessible option for MLX users is mlx-optiq, which provides a drop-in TurboQuantKVCache for mlx-lm models (source 6).

  • mlx-turboquant reports 5x compression and 3.7x speedup at long contexts (source 8).

  • turboquant-mlx offers V2 (hardware-accelerated) and V3 (codebook-correct) paths (source 2).
  • mlx-optiq provides a drop-in TurboQuantKVCache for mlx-lm models (source 6).

Practical Deployment: Server Flags, Batching, and Context Extension

Deploying KV-cache quantization in practice involves more than a single flag. The mlx_lm.server command shown in benchmark reports combines --max-tokens 4096, --max-kv-cache-tokens 65536, --kv-cache-quant q8, --kv-cache-group-size 64, --paged-kv-cache true, and --continuous-batching true (source 5). Paged KV-cache and continuous batching are paired with quantization to manage memory fragmentation and throughput. Alternative runtimes also support quantized KV caches out of the box: mlxcel, a Rust-native MLX inference engine, offers continuous batching, prompt-prefix caching, and quantized KV-cache options (source 11). These features together let users extend context windows without exceeding unified-memory limits.

  • mlx_lm.server combines KV-quant flags with paged caching and continuous batching (source 5).
  • --max-kv-cache-tokens 65536 sets an explicit cache budget (source 5).
  • mlxcel offers quantized KV-cache options, continuous batching, and prompt-prefix caching (source 11).
  • Speculative decoding and 4-bit weight quantization are complementary optimizations (source 1).

Maturity, Quality, and Hardware Acceleration Tradeoffs

The TurboQuant ecosystem on Apple Silicon is still maturing. Integration paths vary in maturity, and users must choose between speed-oriented and quality-oriented implementations (source 6, 2). The V2 path uses hardware-accelerated matmul for speed, while V3 follows the paper-correct codebook for maximum quality (source 2). The native Metal kernel in mlx-turboquant avoids decompression overhead, but it is a custom kernel that may not be portable across all MLX versions (source 8). Benchmark reports emphasize that group size matters more than documentation suggests, indicating that subtle parameter choices can have outsized impact on quality and memory (source 5).

  • Five integration paths exist, with widely varying maturity (source 6).
  • V2 (hardware-accelerated) vs. V3 (codebook-correct) represents a speed/quality tradeoff (source 2).
  • Custom Metal kernels may require maintenance across MLX updates (source 8).
  • KV-cache group size is a critical but under-documented parameter (source 5).

Closing read

Conclusion

The evidence shows that KV-cache quantization is a practical, near-term lever for extending local context windows on Apple Silicon Macs. Multiple independent ports of TurboQuant report 5x compression and meaningful speedups at long contexts, and MLX-LM already ships server flags for KV-cache quantization, group size, and paged caching. These are facts grounded in GitHub repositories and benchmark posts. The quality claims—100% identical output quality in one port—are promising but come from a single source and should be treated as a preliminary result until independently replicated. Projections: as the TurboQuant ports mature, we can expect broader adoption in mlx-lm and alternative runtimes like mlxcel, but the speed/quality tradeoff between hardware-accelerated and codebook-correct paths will likely persist. The key uncertainty is whether custom Metal kernels will keep pace with MLX framework changes and whether group-size tuning becomes standardized across implementations.

Five takeaways

  • MLX-LM server supports KV-cache quantization via flags like --kv-cache-quant q8 and --kv-cache-group-size 64 (source 5).
  • TurboQuant ports on Apple Silicon claim up to 5.5x KV-cache compression and 3.7x speedups at long contexts (sources 2, 8).
  • Unified memory makes KV-cache compression essential: at >16K context, the cache can rival model size (source 9).
  • Group size is a critical parameter that controls scale/zero-point sharing and has outsized impact (source 5).
  • Integration paths vary in maturity, with mlx-optiq offering the most accessible drop-in for mlx-lm (source 6).
